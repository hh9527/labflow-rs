# RFC 0001：Labflow MVP

- 状态：草案
- 创建日期：2026-09-02

## 摘要

Labflow 是用于搭建持续运作的实验室（lab）的使能基础设施。实验室由一份以
DAG 表达的计划驱动。Agent 在实验室中执行工作，supervisor 根据具名制品
（artifact）的状态调度这些工作。

MVP 包含：

- supervisor；
- Host 使用的 CLI 和初始化脚本；
- 用于定义角色、权限、制品及其依赖关系的 `lab-plan.toml`；
- Host 和实验员用于发布制品的文件系统接口。

本 RFC 定义首个外部模型，并记录 supervisor 内部运行模型的核心约束。

## 参与者

实验室中有三类 Agent 参与者：

- **lab-ob**：实验室观察员，也是唯一的主 OpenCode Agent；
- **实验员**：从属于 lab-ob 的 sub-agent，以计划定义的角色开展工作；
- **Host**：控制实验进程的外部 Agent。

计划可以定义 `lab-worker`、`evaluator` 等角色及其权限。这些角色由实验员
承担，并不是额外的 Agent 类别。

supervisor 是 Labflow 基础设施，不属于 Agent 参与者。

## 计划

实验室计划存放在 `lab-plan.toml` 中，并定义一张 DAG。计划描述：

- lab-worker 和 evaluator 角色；
- 各角色拥有的权限；
- 制品；
- 每个制品包含的实验资产或物料，以及构建时需要使用或阅读的资产；
- 制品之间的依赖关系。

计划中的所有相对路径均以 `lab-plan.toml` 所在目录（实验室根目录）为基准。
路径必须规范化，不允许 `.` 或 `..` 分量。

MVP 的计划结构如下：

```toml
version = 1

[backend]
command = ["opencode", "serve"]
hostname = "127.0.0.1"

[roles.researcher]
kind = "lab-worker"
permissions = ["read", "edit"]

[artifacts.query-request]
assets = ["goal.md"]

[artifacts."answer.researcher"]
depends-on = ["system-active", "_ready.researcher", "query-request"]
goal = "goal.md"
assets = ["answer.md", "reports/"]
check = ["answer.md"]
permissions = ["read", "edit"]
```

`backend.command` 是 OpenCode 无头服务器的命令及固定参数；supervisor 会追加
`--hostname` 和 `--port`，其中端口来自 `.labflow/config`。角色的
角色的 `permissions` 是默认的 OpenCode permission 名称列表。worker artifact
可以设置自己的 `permissions`；未设置时继承角色权限，设置后完整替换角色权限，
其中 `permissions = []` 表示不授予任何权限。

逻辑角色名（例如 `researcher`）对应一个稳定复用的 OpenCode session。每个
worker artifact 的有效权限则被渲染为不可变的 OpenCode agent Markdown：先
拒绝 `*`，再允许清单中的权限，并使用固定提示词“你是实验员 <role>，请按照
指令要求完成任务。”。Labflow 对最终文件字节计算 SHA-256，agent ID 为
`<role>.<hash>`，文件为 `.opencode/agents/<role>.<hash>.md`。

agent 文件采用内容寻址，只创建、永不修改。已存在的同名文件必须与预期内容
逐字节一致，否则计划加载失败。发送任务时 supervisor 在 message 请求中指定
本次 artifact 的 agent ID；创建 session 时不设置角色权限。因此同一角色可以
跨阶段保留 session 记忆，同时每个 artifact 使用自己的最小权限执行身份。

## 制品

制品是某项输出或控制事件的名义名称，并不等同于真实的实验输出。每个制品
描述两组资产清单：

- `assets` 是该制品所包含的真实实验资产或物料；
- `inputs` 是需要构建该制品时，实验员需要使用或阅读的资产。

制品将一个或多个真实 asset 作为整体纳入 DAG，使依赖关系和调度只需引用
稳定的制品名，而不必直接依赖具体物料的组织方式。

由 Host 或实验员发布的制品表现为以下目录中的 touch file：

```text
.labflow/artifacts/
```

文件名就是完整的制品名。制品不存在额外的文件名后缀或配套 sidecar 文件。
例如：

```text
.labflow/artifacts/query-request
.labflow/artifacts/answer.researcher
```

这些 touch file 表示对应名义制品已被发布，不承载制品所描述的真实 asset
内容。

### Assets

`assets` 和 `inputs` 中的每一项都只能表示一个文件或一个目录，并使用相对
路径：

```text
reports/summary.md
datasets/raw/
```

目录路径必须以 `/` 结尾；文件路径不能以 `/` 结尾。因此资产的类型直接由
路径形式确定，不需要额外的类型字段。绝对路径不能用作资产。

`inputs` 描述构建工作需要接触的真实材料；制品依赖则描述 DAG 中触发和
调度工作的前序关系。两者是不同的表面概念。

当制品未设置 `inputs` 时，其 `inputs` 默认为所有直接依赖制品的 `assets`
之并集。尚未发布的可选依赖不参与该并集。显式设置 `inputs = []` 表示空的
输入资产清单，不应用该默认规则。

supervisor 根据制品的修改时间判断下游制品是否需要重新输出。具体而言，
当输出制品的修改时间早于某项依赖时，该输出需要刷新。

Host 通过发布或取消发布制品来控制实验进程；publish 会创建或 touch 对应
文件。在 CLI 中，名称前的 `!` 表示取消发布并删除对应文件。

### 命名

制品名由 `part` 构成：

```text
part := [a-z][0-9a-z]*(-[0-9a-z]+)*
```

制品名的形式表示其正常生产责任：

```text
Host：        <part>
实验员：      <part>.<role>
supervisor：  _<part>
             _<part>.<role>
```

对于实验员制品和带角色的 supervisor 制品，角色始终位于点号之后。例如：

```text
query-request
answer.researcher
review.reviewer
_blocked
_ready.researcher
```

在正常调度中，不带点号的制品由 Host 生产；以角色结尾的制品由承担相应
角色的实验员生产；以 `_` 开头的制品由 supervisor 生产。

作为实验进程的外部控制者，Host 可以通过 publish 操作发布任意不以 `_`
开头的制品，包括 `<part>` 和 `<part>.<role>`。例如，Host 可以发布 `aaa`
或 `aaa.researcher`，从而直接干预实验进程。Host 不能发布 `_ready.researcher`
或 `_blocked` 等 supervisor 制品。

Host 也可以通过 `labflow publish !<artifact>` 取消发布任意不以 `_` 开头的
制品。该操作会删除对应的 `.labflow/artifacts/<artifact-name>` 文件。artifacts 目录的
watcher 随后将该文件不存在的事实转换为 Event，使 supervisor 按新的制品
状态重新进行判断。Host 不能取消发布由 supervisor 处理的 `_` 制品。

### Supervisor 制品

以 `_` 开头的制品完全由 supervisor 处理，并且可以参与制品依赖关系。
它们不属于 Host publish 接口可操作的制品。

MVP 保留以下 supervisor 制品：

- `_ready.<role>` 表示某个角色已经具备工作能力。它在任何新会话中均不存在，
  使 sub-agent 可以先基于已有输出开展学习、建立所需认知，再执行后续工作；
- `_blocked` 表示实验室无法继续推进，例如实验员始终不能履行其义务。

## 依赖关系

每个制品可以声明一组制品依赖。例如：

```toml
depends-on = ["query-request", "query-feedback?"]
```

以 `?` 结尾的依赖是可选依赖。`?` 属于依赖语法，不属于被引用制品的名称。

必需依赖不存在时，相关工作不能被调度。可选依赖不存在时不阻止调度；该
可选制品后来被发布或更新时，可以使依赖它的输出再次需要刷新。

计划必须构成 DAG。

## 任务发布

当 supervisor 判断某个制品需要刷新时，它使用固定模板调度负责该制品的
sub-agent。模板如下：

```text
任务: <artifact-name>

要求:
- 按照 <goal.md> 的要求完成任务
- 完成后必须先严格回答“完成任务。”，然后再做其他解释
- 确实无法完成，则必须先严格回答“无法完成任务。”，然后再做其他解释

本次任务的前序工件:
- <pre-artifact-name>: 刚更新
- <pre-artifact-name>: 未改变
- <pre-artifact-name>: 尚不存在

本次任务依赖的文件:
- <goal.md>: 刚更新
- <file-1>: 刚更新
- <file-2>: 未改变
- <file-3>: 尚不存在

你上次发布任务结果不成功的原因是:
- 回答内容不符合要求
- <file-1> 文件不存在
```

其中 `<artifact-name>` 是本次需要刷新的制品名。`<goal.md>` 来自该制品的
`goal` 配置，并作为本次任务的目标说明文件。

“本次任务的前序工件”列出该制品的普通依赖，并标注以下状态之一：

- `刚更新`：前序制品比本次目标制品新；
- `未改变`：前序制品存在，但不比本次目标制品新；
- `尚不存在`：前序制品尚未发布。

本次目标制品尚不存在时，所有已存在的前序制品均标记为 `刚更新`。

以 `_` 开头的特殊制品（例如 `_ready.<role>`）不出现在前序工件清单中。

“本次任务依赖的文件”来自该制品的 `inputs`。未设置 `inputs` 时，按照前述
默认规则取直接依赖制品的 `assets` 并集。目录 asset 必须递归展开，清单最终
列出其中的全部文件，而不是目录名。`goal` 指向的文件也必须列入该清单。

每个依赖文件同样根据文件 mtime 与本次目标制品 mtime 的比较，标注
`刚更新`、`未改变` 或 `尚不存在`。本次目标制品尚不存在时，所有已存在的
依赖文件均标记为 `刚更新`。

失败原因段是可选段，仅在 supervisor 检查到上一次任务失败后的下一次调度
中出现。失败原因包括但不限于：

- sub-agent 的回答未遵守“完成任务。”或“无法完成任务。”的固定回答协议；
- 该制品 `check` 配置所要求的文件不存在。

supervisor 将具体失败原因逐项放入该段，使再次接受任务的 sub-agent 可以
针对上一次失败进行修正。

sub-agent 严格回答“完成任务。”且全部 `check` 通过后，supervisor 代表本次
角色工作 publish 目标制品。sub-agent 只需完成真实资产并作出固定回答，
不需要自行调用 publish 命令。

`check` 没有隐式的默认检查。supervisor 只执行该制品 `check` 字段中明确
配置的检查；制品声明了 `assets` 并不自动产生对应的存在性检查。

`check` 是一组相对文件路径。supervisor 对每个条目只检查对应文件是否
存在，不执行内容检查、命令检查或其他类型的检查。`check` 条目只能指向
文件，不能以 `/` 结尾。任一文件不存在时，本次任务检查失败，并在下一次
调度的失败原因中加入“`<file>` 文件不存在”。

当 sub-agent 严格回答“无法完成任务。”时，supervisor 不再重试，立即发布
`_blocked`。

对于回答格式不符合要求或 `check` 未通过等其他失败，supervisor 最多重新
发布任务三次。每次重试都附带上一次的失败原因。三次重试后任务仍然失败时，
supervisor 发布 `_blocked`。

## Host 控制制品

四个 Host 制品具有内建的控制含义。

### `system-active`

只有 Host 发布 `system-active` 后，supervisor 才会产生新的调度。

`system-active` 依赖 `_blocked`。supervisor 发布 `_blocked` 后，调度停止，
直至 Host 再次发布 `system-active`。重新发布表示 Host 决定恢复实验室运行。

### `system-supervisor`

`.labflow/run` 根据该制品管理 supervisor。制品不存在时不运行 supervisor；
首次出现时启动；mtime 更新时重启；删除时停止。同一 generation 下
supervisor 连续异常退出三次后，`run` 删除 `system-supervisor` 并停止拉起。
稳定运行 30 秒或新的 generation 会重置失败计数。

### `system-backend`

OpenCode 无头服务器作为 supervisor 管理的子进程运行。制品不存在时不运行
backend；首次出现时启动；mtime 更新时重启；删除时停止。backend 通过健康
检查前，supervisor 不调度 Agent 工作。

由此，Host 可以通过统一的制品接口请求 OpenCode backend 受控重启，而不必
同时重启 supervisor。

### `system-plan`

`lab-plan.toml` 是源代码文件，修改文件本身不触发运行时变化。Host 在计划
处于可读取、可校验状态后 publish `system-plan`，表示要求 supervisor 应用
当前计划。supervisor 启动时仍无条件读取一次计划。

计划读取或校验失败不能导致 supervisor 退出。supervisor 暂停基于计划产生
新的调度，并向 Host 请求再次 publish `system-plan`；修复文件本身不触发
自动重试。下一代 `system-plan` 到来后才再次读取。

## CLI 与初始化

MVP 提供以下 Host 命令：

```text
labflow init --port <PORT>
labflow plan check
labflow publish <artifact>... [!<artifact>...]
labflow host-tasks [--poll <seconds>]
labflow status [artifact]
labflow supervisor
labflow run
```

所有命令接受全局 `--root <path>`，缺省为当前目录。`init` 创建示例
`lab-plan.toml`、`.labflow/artifacts/`、初始 `goal.md`、记录 backend 端口的
`.labflow/config`，以及可执行入口 `.labflow/run`。人从独立窗口运行
`.labflow/run` 即建立实验室；进程所有权为 `run -> supervisor -> opencode`。
收到 TERM 或 INT 时，run 删除 `system-supervisor` 并等待 supervisor 自行退出；
supervisor 观察删除事件后负责回收其 backend 子进程并退出。run 不需要向
supervisor 额外发送终止信号。

`publish` 从左到右执行所有参数。普通名称表示创建或 touch，`!` 前缀表示
删除。例如 `labflow publish a b !c d` 发布 `a`、`b`、`d` 并取消发布 `c`。

`host-tasks` 输出 supervisor 当前要求 Host publish 的请求：

```json
{"tasks":["query-request"],"opt":["query-feedback"]}
```

`tasks` 是阻塞流程的必要决策，`opt` 是不阻塞流程的可选决策。artifact 是否
已经存在不是请求的充分判断条件；例如计划加载失败时，已经存在的
`system-plan` 仍会出现在 `tasks`，等待下一次 publish。`--poll 60` 在
`tasks` 非空时立即返回，否则最多等待 60 秒；仅有 `opt` 变化不会唤醒 Host。
该命令只读取 supervisor 写入 `states.sqlite` 的请求投影，不创建
`.labflow/tasks.json`。

## 内部运行模型

supervisor 使用两个 SQLite 数据库：

- `timeline.sqlite` 用于保存供后续分析使用的 timeline record；
- `states.sqlite` 用于保存当前的内部状态，以便 supervisor 重启后恢复。

运行期间，逻辑状态只存在于内存中的 `State`。`states.sqlite` 对 supervisor
的正常运行逻辑而言是只写的；supervisor 只在启动恢复阶段读取它。对
`states.sqlite` 的修改属于 Effect，而不是 reducer 中的数据库操作。
`host-tasks` 可以只读其中专门提供给 Host 的请求投影，但该读取不参与
supervisor 的状态转换。

### Reducer/Effect 约束

内部严格采用 reducer/effect 模式：

```rust
enum Event {
    // 所有能够被 reduce 的事件
}

enum Effect {
    // 所有能够产生外部作用的操作
}

impl Event {
    fn reduce(self, state: &mut State) -> Vec<Effect> {
        // 单线程、确定性的内存状态转换
    }
}

impl Effect {
    fn apply(self, ctx: Arc<EffectContext>) {
        // 执行外部作用，必要时通过 ctx 投递新的 Event
    }
}
```

`Event` 枚举所有能够进入 reducer 的领域事件，包括制品文件变化、session
状态变化等。`Effect` 枚举所有外部作用，包括修改 `states.sqlite`、创建
session、向 session 追问等。

该模式遵守以下约束：

- `Event::reduce` 是唯一能够修改内存 `State` 的位置；
- reducer 同步、单线程运行；
- reducer 不能访问 SQLite、文件系统、网络、时钟或其他外部状态；
- 相同的 `State` 和 `Event` 必须产生相同的新状态和 Effect；
- Effect 执行期间不能读取 `State`；
- Effect 必须携带执行所需的信息；
- Effect 可以通过 `EffectContext` 投递新的 Event，但不能借此反查 `State`。

该约束适用于所有异步和外部操作，而不仅是制品调度：

- `run` 所持有的 supervisor 进程和 supervisor 所持有的 OpenCode 进程都由
  reducer 保存逻辑状态；进程 actor 只能持有 OS handle、执行 Start/Stop
  Effect，并将 Started/Exited/Failed 事实投递为 Event，不能自行决定重启；
- 计划读取和等待下一代 `system-plan` 由上层 supervisor reducer 发出 Effect，
  读取成功、失败或等待结束均转换为 Event；
- 所有 OpenCode HTTP API 请求，包括创建 observer session、创建角色 session、
  向 session 发送任务等，均由 reducer 先记录 pending 状态，再发出 Effect；
- 文件检查和制品发布等其他外部操作同样只能由 reducer 发出 Effect；
- 异步 Effect 及其完成 Event 携带 request ID 或 artifact generation。reducer
  只接受仍与当前状态匹配的完成事件，过期响应不能改变状态；
- 运行代结束时取消并回收该代尚未完成的 Effect task，不能让旧计划的本地
  Effect 继续投递到新计划的状态机。

启动时从 `states.sqlite` 恢复内存 `State` 属于 supervisor 的 bootstrap 阶段，
不属于正常运行期间的 reduce 流程。

### 外部信息摘取

OpenCode 的流接口或 HTTP API 是外部信息来源。摘取层将其中的信息分为两类：

- 一部分转换为 timeline record，直接写入 `timeline.sqlite`；
- 一部分转换为 Event，投递到单线程 reducer 的事件队列。

同一份外部信息可以同时产生 timeline record 和 Event。timeline record 用于
分析，不参与 reducer 决策；Event 只携带当前状态转换所需的领域事实。

`.labflow/artifacts/` 的 watcher 是另一个外部 Event 来源。Host 或实验员
创建、touch 或移除制品文件后，watcher 将观察到的文件事实转换为 Event，
再由 reducer 更新内存 State 并决定后续 Effect。watcher 不能直接修改
`State` 或发起调度。

supervisor 启动时对 artifacts 目录的初始扫描也转换为 Event，走相同的
reduce 流程。watcher 可能产生重复通知，因此相关 Event 表示观察到的当前
文件事实；reducer 根据制品名及其文件状态进行幂等处理。

整体数据流如下：

```text
OpenCode stream / HTTP API ──> 信息摘取 ──> Event ─┐
                                                   │
artifacts 目录 watcher ────────────────> Event ─────┼─> 单线程 reducer
                                                   │        │
其他外部信息源 ───────────────────────> Event ─────┘        ▼
                                                         Effects

OpenCode stream / HTTP API ──> 信息摘取 ──> TimelineRecord
                                                   │
                                                   ▼
                                            timeline.sqlite
```

## MVP 边界

首个实现关注计划、制品协议、supervisor、Host CLI 和初始化脚本。

对 lab-ob 内容和 Agent 历史行为的数据分析不属于 MVP。将来可以在不改变
本 RFC 所定义的制品命名和控制表面的前提下增加相关能力。

## 待讨论问题

更丰富的状态诊断、timeline 分析接口和角色权限表达能力留待后续 RFC 扩展。
